# E 审查正式 Scope Mission 创建事件

审查 D #301 精确源 `ce81483e9c56d8b52e671493f89daa0f7da6ca3e`。接受独立纯验证器施工，范围是候选正式单行字节、初始字段、摘要及回执数据的结构检查。正式类型注册、全账本查找、投影与生产写入继续 HOLD。

- 现有 R1 `_canonical_payload` 按 artifact_type 选择 validator，映射新类型到 rc7_mission 本身无法校验初始态、原始标识或包元数据。回放默认先尝试 legacy 容器展开。新事件必须在通用展开和 Mission 归一化之前走专用校验。独立验证器应直接接收原始 bytes，严格解码后一次验证 7 个外层键、20 个 payload 键、固定类型、两级版本、四个空数组、null 评估及单次整数 Unix 秒。外层 seq 为正 bigint，任何版本、序号和时间中的布尔值均拒绝。校验原 goal、镜像和映射，重建 #288 摘要，逐字比较原事件携带的摘要与所有复合身份。
- 规范新事件行使用 #288 的 UTF-8/JSON 精确规则和单个 LF，整行重新编码后应与输入逐字相等。原始回执哈希计算移除该 LF 后的原始 bytes。可复用已接受的严格解码与原行提取，单行验证器需拒绝空白行、额外行、CRLF、缺终止符、重复键、非整数数值以及合法 JSON 的不同表示。旧 R1 文本模式可能跨平台转换行结束符。新类型写端的原始 LF、fsync 和失败恢复仍需单独证明。
- 实际旧 `JsonlEventStore.append` 在临时账本成功写入未知字段 `historic_unknown_metric: NaN`，旧 `TruthRuntime` 冷读两条 Mission 均成功，当前严格快照解析拒绝第一行。探针同时用 native append 的 event_id 参数写入两个相同 event_id，并在临时夹具强制两条 seq 均为 1。旧冷回放保留两行，下一 seq 为 2。正式启用必须显式区分普通旧回放和正式账本资格：保持已支持旧路径语义，整账本不能满足正式严格扫描时返回 HOLD。若以后需要容纳此类旧行，须先设计并验证双读兼容协议，尤其不能用宽松解码的最后一个 event_type 判定是否需要严格校验。
- 正式 event_id 查重应覆盖同一固定物理账本的原始事件，包括可能使用相同 event_id 的旧行，不能只核正式类型。物理行位置、原字节、严格元数据与原权威同时核对，seq 不能独立标识原事件。首次匹配之后继续检查全账本，检测重复、相斥 K、旧 Mission 身份及后续未经授权更新。独立单行解析通过只证明结构，不能签署来源唯一、许可、scope 或正式完成。
- 现有 `AdminProjection.get_resource` 与 `mission_overview` 返回原 Mission 对象。现有 `mission_overview_scoped` 只返回三个身份字段，但平面 project/batch 通过后即读详情。因此上线前要验证正式绑定记录不能进入旧明细路径，旧 Admin 路线也不能返回包含 actor、creation key 与回执引用的正式内部结构。保留现有平面 fixture 的能力，正式读按独立来源及授权合同进入。
