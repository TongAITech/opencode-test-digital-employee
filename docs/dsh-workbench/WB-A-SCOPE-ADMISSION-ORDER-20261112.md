# 正式创建与业务撤权的持久顺序候选

基线 `b05f7f3ef1f2619394cf75023d3dea5c437f4864`，输入 B #265、D #267 与 E #272。本文请求评审跨存储的提交顺序。现有 V3 权限检查、HostFence 和 R1 事实边界继续适用。

## 必须跨越的故障点

E #272 在真实 PostgreSQL 17.6 中完成最后一次 SELECT，终止持锁连接，然后观察实际 ACL 撤权提交。锁释放和 R1 durable append 之间没有共同事务。增加一次心跳仍有相同的故障窗口。

当前 `JsonlEventStore` 只在实例中使用线程锁，`append_atomic` 会先追加并 fsync，再执行本实例投影验证。异常可以发生在 durable append 之后。Worker assignment 的独立锁文件也只由特定入口使用。既有两种锁均缺少正式创建所需的跨入口、跨进程排他证明。

## 提议的顺序

1. 维持 008 的独立 PREPARE，保存原 K、请求字节和预留 ID。PREPARE 不占用业务撤权围栏。
2. 只有经审查的 R1 创建写入器可以取得该物理账本的独占写入权，并在当前 R1 游标上识别同 K 的原事件。写入权需要覆盖正式创建及所有可能影响其源唯一性的入口。先取写入权，随后进入 PostgreSQL。
3. 在一次 PostgreSQL 事务内锁住项目及批次，复验当前主体、Scope 及来源，然后持久登记仅绑定原 K、digest、operation、writer epoch 与账本的提交中记录。未确认该事务已提交时停止并查询原 K。已有项目、批次、ACL 或关联变更的正式提交路径必须在相同项目／批次行顺序下发现该记录。变更必须等待经核验的清理，或返回明确可重试的冲突。单独的 advisory lock、会话断连或租约到期不得清除记录。
4. 写入器仍持独占写入权时，经独立 HostFence 提交到 R1。账本 fsync 成功并且原事件可验证后，在 PostgreSQL 对账并清除该记录。正式事件已写入但回执未知时，保留围栏，由恢复路径在同一写入权下冷读账本。
5. 恢复路径首先取得同一账本写入权，再按原 K 和 operation 检查原始事件。唯一且相符则登记原回执。只有完整原账本能证明未写入，且旧写入者已无法再追加时，才能释放围栏并保留原 intent。损坏、歧义或无法读取持续 HOLD。恢复不得自行调用新建。

这会改变项目撤权和关联更新的可用性。项目在恢复前可能返回冲突，尤其是账本不可读时。B、D、E 与 A 需要明确该行为是否满足撤权时限，并核对各个现有源写入口。若要求撤权在账本不可用时仍能立刻完成，应改用具备共同提交顺序的权威机制。不得让当前产品根据本文启用任何正式写入。

## 测试退出条件

- 实际 PostgreSQL 两个连接及两个独立写入进程复现两种先后次序。撤权先提交时禁止追加，创建先持久提交时随后撤权不得删除既有事实。
- 在 PREPARE、提交中记录的事务回包、最后一次 PG 校验、R1 fsync、回执保存和清理前后分别终止连接与进程。恢复必须校验原 K，精确区分零次或一次真实事件。
- 源锁须覆盖 ACL、日期和关系的各正常入口，另验 DDL、管理员运维和进程托管边界。验证账本路径别名、进程重启、未遵循围栏的旧写入器、重复源事件、截断尾部、时限和恢复后的旧写入者。
- 验证恢复期间读取和变更的契约行为，并实测不可用窗口。真实 Host 的撤权全序由原 Host 权威单独证明，行内证据继续待搬运。
