## P1: native browser fetch is invoked with an invalid receiver

`rc7_admin/static/workbench/runtime-panel.mjs:11` defaults `fetcher=fetch`; RuntimeClient stores it, then `rc7_admin/static/workbench/runtime-client.mjs:63` calls `this.fetcher(path, ...)`. The receiver is the RuntimeClient object, rather than Window. Chromium rejects the native function with `TypeError: Failed to execute 'fetch' on 'Window': Illegal invocation`. The catch converts this into `TRUTH_SOURCE_UNAVAILABLE`.

Independent real PostgreSQL → HTTP → Chromium probe: the first window has an explicitly injected arrow fetch wrapper for delayed-response testing; it loads Scope and the initial runtime snapshot. A second window in the same context has **no fetch injection**. Its business Scope successfully reaches READY. Reading M1 on Gates immediately reaches ERROR/TRUTH_SOURCE_UNAVAILABLE and emits no graph/workitems/quality requests. A direct browser receiver control reproduces the same native TypeError. Thus the failure occurs before the business API is contacted, and is not a Scope, R1, Gate fixture or PostgreSQL failure. Tasks uses the same affected client.

The candidate browser suite installs an arrow fetch wrapper and therefore does not expose this native default path. The affected call predates this PR; its presence in the exact candidate still blocks acceptance of the new Gates user flow. The earlier F runtime UI acceptance also did not cover this unwrapped path and must not be cited as evidence that it works.

Expected: an ordinary window can load runtime facts without test-only fetch replacement. Required independent recheck after a new frozen SHA: ordinary unwrapped first and second windows, plus existing wrapped cancellation probes. F does not prescribe or implement the fix.
