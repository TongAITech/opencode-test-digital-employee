## CC-01: typed non-Mission R1 root

GeneralWorkItem and RuntimeDiagnosisJob are first-class roots. Their lifecycle must use the existing canonical `commands` and append-only `events` transaction infrastructure. A separate mutable workflow store, fake Mission, or reuse of Knowledge facts as job state is prohibited.

The existing v1 envelopes and SQL column `mission_id` currently name the stream key. To preserve existing event bytes, fingerprints, and hashes, retain that storage field as a documented compatibility name; introduce a typed SubjectRef API above it. GeneralWork public interfaces expose `job_id`/`subject_kind`, never a counterfeit `mission_id`. New root IDs use disjoint runtime-created namespaces. A root's type is derived from its immutable creation event owned by its registered extension, not trusted from a model payload. No new Mission-created event or Mission projection row may appear for general work.

Amend the extension manifest with explicitly reviewed root ownership, creation commands, and state existence validation. Only the registered root owner's commands may operate without a Mission. Root creation requires an empty stream and expected sequence zero; existing roots require exact current sequence. Mission-centric extensions remain Mission-only unless their reuse is explicitly reviewed. An unregistered root cannot receive generic writes. CORE CREATE_MISSION cannot claim an occupied GeneralWork stream, and GeneralWork cannot claim an existing Mission stream. Existing runtime get_state/get_composed_state retain their Mission precondition; add a typed root accessor for non-Mission work.

Composed replay advances the shared event sequence and invokes only owned reducers. Projection application/rebuild must skip Mission projection for an explicitly valid non-Mission root and use the extension's regenerable projection. No projection is authority. Restore/replay tests must compare on-disk events, projection hashes, Mission count, and root type before/after restart; transactional failure injection and stale CAS tests must demonstrate no partial writes. Existing Mission event bytes and results must remain unchanged. Downgrade may read unaffected Mission streams; old binaries must not claim support for new root commands. Rollback preserves all R1 history and fences unsupported active jobs instead of dropping their data.

### CC-01 review amendments (mandatory)

Extension applicability is deterministic per immutable root kind. Mission initialization/serialization/projection/verification must retain the baseline applicable extension set and golden composed hashes; GeneralWork-only registration must not add empty keys to existing Mission state. Both the live command bus and replay validate sequence-1 root event, namespace, owner, creation command/event pair and entity identity. Repeated/forged/unknown creation and pre-root extension events fail closed.

Cross-root references resolve under exact SubjectRef: Task, Attempt, session, lease and idempotency key cannot silently refer to another job or Mission. Related Mission references are explicit governed links, never alternate ownership. Reuse the existing pure Scheduler readiness/selection policy through a typed subject scheduling port: the subject owner applies durable dispatch events, Router provisions real sessions, and shared pure selection/resource policy decides eligibility. Do not enable all Mission extensions for GeneralWork or duplicate a scheduling authority. This extraction must preserve existing Mission behavior and be tested under the same liveness matrix.

Root-aware load, verify and full rebuild must enumerate and validate every stream owner/version before clearing projections, then rebuild all supported types in the existing transaction. Unknown/omitted owner, future version and injected clear/apply failure cannot return success with lost GeneralWork projections. Golden old events, historical command results/fingerprints and composed-state hashes are mandatory compatibility evidence. There is no claim that an unmodified old binary can safely initialize/rebuild a mixed-root database. A runtime compatibility guard must stop dispatch/rebuild on unsupported root versions; rollback restores compatible executable/state handling while preserving the complete event history. Explicitly scoped legacy Mission reads are separate from writable downgrade.

Independent source review: `reviewer-architecture/CC01_INDEPENDENT_REVIEW.md`, six requested revisions above. Their incorporation is a design decision, not a test PASS.

### CC-01 immutable interaction receipt amendment

`INTERACTION_OPERATION` is an additional registered R1 root used only to consume actual Host User Turn authority atomically before its destination is resolved. It carries an immutable Host envelope digest, operation identity, request digest and eventual exact SubjectRef, with CLAIMED → BOUND / COMPLETED / RECONCILE_REQUIRED transitions validated by its owner. It is an authorization receipt, not a work item: it must never acquire Tasks, a Scheduler, worker Sessions or a fabricated Mission. Destination creation and binding use deterministic identities; an interrupted claim is reconciled before any retry. Repeated model proposals cannot spend the same actual operation twice. No separate mutable receipt database is introduced.

This is a component amendment authorized by F53's consumed-turn/idempotency requirement and preserves the v7 sole R1 truth invariant. Root-kind applicability, creation-pair validation, mixed-root replay/rebuild and downgrade guards above apply equally to the receipt owner. Implementation and end-to-end admission evidence remain required.

## CC-02: intake, authority, and actual delegation

The nine V4 intent classes and independently scoped mixed-turn operations share actual HostToolContext provenance. Semantic classification proposes purpose and arguments; it does not grant authority. Each admitted operation binds actual user message/parent/session, immutable content digest, expiry, consumption/idempotency state, resolved subject, and effect scope. Quoted, negated, synthetic, replayed, stale, and model-invented requests cannot confer execution authority. No empty-scope Mission deduplication. Zero/one/many matching durable subjects yield resolve/continue/one necessary clarification respectively. Pause/stop preempt fresh dispatch.

Primary receives query/admission/delegation/control/Gate interfaces. General Worker and Runtime Diagnosis have callable real tools with runtime-issued leases. A lease binds subject, caller, session, epoch, operation classes, read/write roots, network boundary, process/time/output budgets, expiry and policy revision. Protected R1, auth, governance, frozen cases/oracles, receipts, sealed code and other active jobs are excluded from direct general file mutation. Atomic writes require expected digest and conflict-safe backup; engineering output is not formal Case PASS. Runtime diagnosis can repair regenerable state or produce an isolated tested upgrade candidate, not rewrite active permissions/oracles.

## CC-03: operating-system effects and brokers

Tool allowlists and Python wrappers are not the security boundary. Windows capability execution requires tested no-admin OS confinement and separate trusted brokers. AppContainer is under actual CI evaluation with standard-user positive I/O/process controls, direct/traversal/case/junction protected-state attacks, inherited descendants and affirmative TCP denial. A failed positive control is not a sandbox pass. Compatibility with portable Python and Git Bash, remote egress, named pipes/COM, and bank lockdown remains gated until measured. Unsupported isolation disables only affected execution capability and leaves explicit technical status; it cannot silently become an unrestricted shell.

Browser workers must not obtain direct unconstrained CDP or broker credentials. All actor, default/custom tool and raw protocol paths require the same operation/epoch/G4 admission at the process transport boundary. A Python monkeypatch alone cannot prove this. Process ownership is separate from engine/session lifetime; independent owned Chrome survives engine reattachment and HumanGate preparation. Existing bank browsers are never assumed owned from a port alone.

## CC-04: progress and context

One supervisor delegates scheduling to existing Scheduler and routing to existing Router; GeneralWork is another typed subject, not another scheduler. Accepted business receipts, unit processing, case/step/evidence progress drive liveness. Heartbeats are insufficient. Busy, async in-flight, legitimate Gate, backoff, compact/rotate, pause/stop are checked before bounded AUTO_CONTINUE. Repeat failure signatures have bounded wake/diagnose/repair escalation and durable cursors.

A final serialized-request hook must count actual request bytes separately from estimated tokens and model limits, including history/tools/arguments/results. Provider metadata and measured limits carry provenance/confidence. All roles use the same admission layer. Compact is bounded; failure recovers deterministically from durable state into a clean non-fork successor. Fence old epoch before binding successor; recover crash windows idempotently. TUI pointer follows only verified successor. Component hook experiments are not product automatic rotation qualification.

## CC-05: side effects and oracle truth

Each mandatory oracle has a stable unique ID and independently retained result; aggregation cannot overwrite by channel or later success. Missing/error/unknown observations cannot become PASS. Durable outbound intent, sent boundary, request identity, cursor/variables and receipt precede/follow actual external action. A crash after possible send enters UNKNOWN_SIDE_EFFECT and forbids blind reissue. Reconcile through verified idempotency/correlation/readback or explicit human decision; arbitrary bank endpoints have no exactly-once promise. Same-attempt replay cannot hide duplicate business writes.

V4 authorizes construction of G6-A through G6-H and supersedes old blanket construction exclusions. It does not assert an approved activation policy.
