## Finding P1-G3-01 — mixed mapped + unmapped changed lines still silently disappear

The repair decides language truth at **file/provider level**:

```python
if changed and not mapped:
    PARTIAL
else:
    AVAILABLE
```

This means one mapped declaration-line change is enough to report `AVAILABLE/COMPLETE`, even when another changed body line in the same file is not mapped to any symbol.

Independent real-Git reproductions:

### Java

Changed lines:

```text
src/A.java:L2   # declaration rename => maps foo2
src/A.java:L6   # body-only change in bar => unmapped
```

Actual result:

```text
JAVA = AVAILABLE
repository status = COMPLETE
warnings = CODEGRAPH_UNAVAILABLE only
changed_symbols = foo2 only
```

The changed body of `bar()` silently disappears from symbol truth.

### TypeScript

Same mixed pattern:

```text
TYPESCRIPT = AVAILABLE
status = COMPLETE
only changed declaration symbol is emitted
body-only changed method is missing
```

### Vue

Same result:

```text
VUE = AVAILABLE
status = COMPLETE
one mapped declaration hides another unmapped body change
```

This violates the frozen requirement that non-Python change semantics must not silently disappear.

Required narrow repair:

- compute mapping completeness per changed executable line / hunk, not merely `mapped != []`;
- if any relevant changed lines remain unmapped, mark that language/repository `PARTIAL`;
- emit explicit `MISSING_SYMBOL_MAPPING` obligations containing the **unmapped changed_line_refs**;
- or replace regex providers with real enclosing-symbol parsers.

**Decision: `G3 = NARROW_ENGINEERING_REPAIR_REQUIRED`.**

# 9. G4 review

The repair contains substantial real implementation and fixes several original defects, but four closure blockers remain.

## Finding P1-G4-01 — canonical product surface can persist fabricated execution truth without a G3 governed case/batch

Formal design freezes:

```text
G3 decides how to test and why.
G4 executes the governed result.
```

`create_batch()` correctly validates:

- `CASE_SPECIFICATION`;
- strategy version;
- `CASE_VALUE_LINK`.

But **that governance is not required by the actual execution surfaces**.

### `record_step_result()`

It requires a real canonical ExecutionAttempt, but accepts arbitrary:

```text
case_id
case_version
expected
actual
oracle
evidence_refs
source_identity
```

It does not prove the case exists in G3 or belongs to any G4 ExecutionBatch.

The OpenCode/product surface exposes this method directly as an `EXECUTOR` action.

Independent reproduction using a real canonical Mission/Task/ExecutionAttempt:

```text
case_id = FAKE-CASE
case_version = FAKE-V1
no G3 CASE_SPECIFICATION exists
no G4 ExecutionBatch exists

record_step_result(...)
=> ACCEPTED
=> durable EXECUTION_STEP_RESULT written to R1
```

### `execute_capability()`

It has the same case/batch gap.

Independent reproduction:

```text
real canonical ExecutionAttempt
real bound deterministic API executor
case_id = FAKE-CASE-2
case_version = FAKE-V2
no G3 governed case
no ExecutionBatch

execute_capability(...)
=> execution = COMPLETED
=> PASS
=> durable EXECUTION_STEP_RESULT for FAKE-CASE-2
```

G3 contains no such cases.

This means a valid Executor Session can bypass G3 Case/CaseValueLink/Batch governance and create apparent “real execution evidence”.

Required repair:

- introduce one canonical governed execution binding validator used by `record_cursor`, `execute_capability` and `record_step_result`;
- require exact G3 `CASE_SPECIFICATION` / case-version / strategy / CaseValueLink identity;
- require a durable G4 `ExecutionBatch` (or an explicit governed focused-execution binding) containing the case;
- preferably remove raw `record_step_result` from the public OpenCode Executor surface and make it an internal result sink from a verified capability execution receipt;
- if manual execution needs a reporting seam, require a canonical Manual/HumanGate execution receipt rather than arbitrary caller assertions.

This is a G4 Engineering closure blocker.

## Finding P2-G4-04 — terminal TestingGoal states are not enforced as terminal

The repair now durably writes `TESTING_GOAL_STATUS` facts, which is an improvement.

But `_set_goal_status()` only checks that a target status is in the allowed vocabulary. It does not enforce legal transitions or terminality.

Independent reproduction:

```text
goal reaches 96%
evaluate_goal()
=> SATISFIED
goal_status = SATISFIED

a later bank measurement is recorded
=> _set_goal_status(... MEASURING)

goal_status becomes MEASURING
```

So `SATISFIED` is not terminal even though the frozen state model defines it as terminal.

Required repair:

- enforce a transition table;
- terminal states cannot return to non-terminal states;
- changed release/source after terminal completion should create/supersede a new goal/revision, not silently reopen the same terminal goal.

## Finding P2-G4-05 — secret sanitization remains heuristic and leaks plausible credentials

The new sanitizer is materially better and correctly redacts labeled values such as:

```text
otp=482911
password=hunter2
Bearer ...
JWT-like values
```

But the frozen invariant is stronger: password/OTP/captcha/auth material must never become durable evidence/knowledge.

Independent inputs still pass through unchanged:

```json
{"actual":{"token":"abc123XYZ"}}
{"evidence_metadata":{"cookie":"JSESSIONID=abcd1234"}}
{"actual":{"session_id":"abcdef123456"}}
{"actual":"hunter2"}
```

Only a labeled form such as:

```text
cookie=...
```

is redacted.

No regex can reliably infer that an arbitrary string is a password. Therefore the proper fix is not an ever-growing regex list alone.

Required repair:

- add sensitive/taint classification at executor/browser/API evidence ingress;
- never capture auth-entry values from controlled browser evidence;
- explicitly classify/redact token/cookie/session/auth fields before durable-write;
- keep current pattern sanitizer as defense-in-depth;
- add adversarial tests for generic token/cookie/session/auth-body channels.

# 11. Why 289/289 and 60/60 still missed the remaining defects

The new adversarial suite attacks the exact previous findings, but some oracles are still narrower than the frozen design:

1. Multi-language test covers **zero mapped symbols**, not a mixed file where some changed lines map and others disappear.
2. Goal lifecycle test proves a terminal status is written, but does not attempt a later illegal transition.
3. Secret test uses labeled secret strings, not unlabeled token/cookie/session values.
4. AUTO test proves runtime verification when `complete_human_takeover()` is called; it does not prove a background observer invokes it automatically.
5. No test requires execution actions to prove a G3 Case/CaseValueLink/ExecutionBatch binding.
6. No coverage test attempts to satisfy a V2 goal with a V1 bank snapshot.
7. Static audit validates presence of code patterns, not these behavioral counterexamples.

Therefore:

```text

+
60/60 static PASS

does not imply

all frozen G3/G4 design invariants are implemented.
```
