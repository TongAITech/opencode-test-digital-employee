# 10.REC.3 — OpenCode process and approved host provider binding

The pinned package host is OpenCode 1.18.3. OpenCode process readiness, Control Loop operation, model configuration, credential verification, model response, and actual Session admission are separate observations. No model binding or credential prompt runs before process startup. A missing or malformed binding yields `AUTH_REQUIRED`; a provider initialization failure gets one bounded restart with a provider-free configuration. Actual runtime/integrity failures remain failures.

The daily entry checks installed identity and all sealed package hashes before runtime imports, source materialization, or state initialization. OpenCode starts on authenticated loopback; `/global/health` confirms the process independently of provider initialization. The Control Loop starts next. A real Director entry Session is then created or recovered and passed to `opencode attach --session`; an auth-pending Session title carries setup guidance without an LLM call. `R2_SESSION_READY` is emitted only after a real Session is returned. Startup diagnostics are operational projections, not a replacement for R1 Mission Truth. No startup probe claims `AUTH_READY`, `LLM_RUNTIME_READY`, or a bank response merely from HTTP health.

## Pinned source reconnaissance

The implementation was checked against the exact public `v1.18.3` tag, not the moving default branch:

- [Config loading and precedence](https://github.com/anomalyco/opencode/blob/v1.18.3/packages/opencode/src/config/config.ts): global config is merged before custom, project, `.opencode`, and inline config. Loading a file without `$schema` may write `$schema` back to that source file. Consequently, passing the host config through `OPENCODE_CONFIG` would violate the no-host-write boundary and is not used.
- [Config search paths](https://github.com/anomalyco/opencode/blob/v1.18.3/packages/opencode/src/config/paths.ts) and [global paths](https://github.com/anomalyco/opencode/blob/v1.18.3/packages/core/src/global.ts): XDG data/config/cache/state are distinct; home `.opencode` discovery also exists. The package isolates all four XDG roots and uses the pinned `OPENCODE_TEST_HOME` path override to keep home plugin discovery inside package data. Host auth stores are not imported.
- [Provider SDK resolution](https://github.com/anomalyco/opencode/blob/v1.18.3/packages/opencode/src/provider/provider.ts): a configured `npm` SDK may be a `file://` URI; OpenCode imports its `create*` factory and requests its language model. A custom SDK does not require an OpenAI-compatible URL.
- [Plugin resolution](https://github.com/anomalyco/opencode/blob/v1.18.3/packages/opencode/src/config/plugin.ts) and [plugin hooks](https://github.com/anomalyco/opencode/blob/v1.18.3/packages/opencode/src/plugin/index.ts): local plugin references are valid, and plugin authentication loaders are separate from provider SDK selection.
- [Offline dependency check](https://github.com/anomalyco/opencode/blob/v1.18.3/packages/core/src/npm.ts): OpenCode checks dependencies for each configuration directory; plugin/tool startup can wait for these checks. `prepare()` copies the shipped, verified plugin dependency tree and package manifests into the package-owned global config directory when absent. It invokes no package manager. This also prevents a blank isolated XDG directory from triggering a dependency download during custom plugin initialization.

## Explicit binding contract

`HOST_OPENCODE_CONFIG_DISCOVERY` only checks candidate file existence and size. It captures original XDG/custom config paths before package isolation. It neither parses host config nor opens an auth store. An unreadable candidate is skipped; it cannot prevent process startup.

Menu 5 offers `REUSE_APPROVED_HOST_PROVIDER`, `PACKAGE_LOCAL_PROVIDER_BINDING`, and `AUTH_REQUIRED`. Host reuse requires an explicit config path and approval reference. The prompt explains that this approval permits bounded config inspection and execution of the existing local SDK/plugin code. Config inspection handles JSON and JSONC, is limited to 1 MiB, and never displays raw content. Only safe model identifiers are displayed.

The persisted binding contains mode, source path, selected `provider/model`, approval reference, and source/module hashes. It contains no provider options, API key, password, token, or auth-store content. On startup, the approved source is checked again and only the selected provider/model plus local plugin references are projected into process-local `OPENCODE_CONFIG_CONTENT`. Host agents, tool permissions, commands, MCP, instructions, and general settings are not imported. The host config is never passed to OpenCode or changed by the launcher.

Inline credential fields are rejected. Credential and header values must be environment references; `{file:...}` references are refused without opening their targets. URL credentials/query/fragment values are refused. SDKs and plugins must already exist locally; relative paths and installed modules are resolved against the approved host config directory, converted to file URLs, and hash-bound. Changed config/module bytes require reapproval. Remote/missing npm modules do not trigger installation. Arbitrary approved plugins are executable code, so their real bank authentication behavior and dependency compatibility remain a bank qualification obligation.

Package-local OpenAI-compatible addresses are preserved exactly; `/v1` is never appended or demanded. Existing package-local configuration remains usable. Credentials are inherited through approved environment references and are never collected in a model prompt or saved by the launcher.

## Qualification boundary

`test_recovery_startup_provider.py` uses actual pinned OpenCode and Control Loop processes on the normal `start_conversation` path, replacing only terminal attachment with an observation callback. It verifies auth-pending startup, actual Session creation, heartbeat, installed identity/integrity on Windows, and secret-free discovery/binding. It also loads a synthetic local plugin and a custom local SDK as `wizard-local/aicoder-plus`, with no endpoint or `baseURL`, then obtains a synthetic model response through the real OpenCode API. That proves the supported configuration mechanism, not compatibility with the bank's unprovided plugin or authentication system.

`HOST_PROVIDER_DISCOVERY = PARTIAL_BANK_BINDING`; `BANK_PROVIDER_BINDING_REQUIRED` and `BANK_FIELD_VALIDATION_REQUIRED` remain explicit until the actual bank SDK/plugin, auth environment, dependencies, and model response are verified. The fixture is not Real BLOAN Bank PASS.
