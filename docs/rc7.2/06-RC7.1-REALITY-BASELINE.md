# RC7.1 Reality Baseline for RC7.2 Construction

Status: FROZEN INPUT TO RC7.2 CONSTRUCTION

This document records the RC7.1 field/runtime reality that RC7.2 construction must preserve or deliberately replace. It is not a claim that every capability below is fully field-qualified. Repository code, R1 truth, CI and field evidence remain authoritative.

## 1. Construction ancestry

- RC7.1 Field Turnkey baseline: `366e196826afb3be17d2811044699891bdd28ea5`
- RC7.2 frozen design baseline: `a3426e306abf967ab822d44508127c3891c8e91e`
- RC7.2 construction branch: `work/rc7.2`

RC7.2 is an in-place runtime evolution. It must not build a second shadow control plane beside the inherited R1/event/projection runtime.

## 2. Existing reusable runtime reality

The current codebase already contains reusable RC7 control-plane primitives:

- canonical `Mission`, `Task`, `Artifact`, `Evidence`, `Gap`, `Evaluation`, `EventRecord` models;
- an R1 truth overlay using the inherited append/replay/projection mechanism;
- durable acceptance enforcement for PASS/RESOLVED/CONVERGED states;
- deterministic `GapRouter` policy;
- parent-derived Test Design obligation inventory from accepted Requirement/Code artifacts;
- Mission graph v1/v2 compatibility contracts;
- signed Worker lease/runtime controls and Field-vs-Worker authorization separation from RC7.1;
- existing DB/CAT/Libra/CodeGraph/Browser/4A and L1-L7 integration work that must be reused rather than mocked.

These are assets, not reasons to skip RC7.2 domain/state-machine work.

## 3. Current graph/runtime limitation

The existing Mission graph v2 is a responsibility graph with six durable top-level tasks and additional logical/runtime stages. It is useful compatibility infrastructure, but it is not yet the frozen RC7.2 N1-N10 canonical state machine.

RC7.2 must therefore add first-class N1-N10 MissionNode truth without silently changing persisted RC7.1 graph identity.

## 4. Field observations driving RC7.2

The BLOAN-PF1.2.1 92% incremental-coverage mission exposed the following structural issues.

### GAP-01 Startup authentication sequencing

DSH Web can start before model authentication/provider readiness. Expired authentication can leave the UI indefinitely loading until a later restart recreates the provider client.

### GAP-02 Task decomposition

Current execution commonly uses large round batches instead of small, homogeneous, independently recoverable ETUs. Target RC7.2 default is 3-8 cohesive cases per ETU with adaptive split/merge/reprioritization.

### GAP-03 Journey Teaching

Business-flow teaching/recording, DOM+Network capture, Journey Compiler, replay/benchmark and reusable L4/L5 Journey assets are not yet productized end to end.

### GAP-04 Model failover

A provider quota failure can block an AgentTeams member because an existing member/session cannot simply switch models. RC7.2 must migrate the WorkItem to a fresh Worker/Attempt rather than mutate the old session in place.

### GAP-05 Browser resource isolation

Captain/AuthKeeper and L4/L5 Workers can contend for the same BSK/browser control plane. RC7.2 requires BrowserPool/BrowserLease and exclusive WRITE ownership.

### GAP-06 Dynamic capability escalation

Workers correctly remain STRICT, but a missing capability currently lacks a complete CapabilityRequest -> temporary lease/delegation -> resume path.

### GAP-07 Stage boundary/readiness enforcement

Field evidence shows the executor performing work that belongs to earlier stages: reading source to infer payload fields, discovering DB constraints, repairing data selection and revising effective test design during execution. RC7.2 must enforce N2-N6 sufficiency/readiness before N7 and route failures through N8 semantic back-edges.

### GAP-08 Coverage-centric organization drift

Test assets/tasks have drifted toward Libra coverage-gap/round organization. The canonical organization must instead be:

`ReleaseBatch -> Version/Application -> Requirement -> SST -> TestObligation -> L1-L7 -> TestCase -> ETU -> WorkItem -> Attempt -> Evidence`

Coverage is a feedback/convergence signal and prioritization input, not an asset root or direct case generator.

## 5. Additional consequences already observed

The following consequences are considered part of the structural gaps above and must not be treated as unrelated patches:

- long-lived Captain/executor/designer/auditor/reviewer sessions and context growth;
- lack of systematic Fresh Worker and Fresh Reviewer rotation;
- occasional mismatch between Agent-reported completion and canonical R1 stage/lease truth;
- need for true Captain session handoff based only on R1;
- provider/auth/quota errors mixing with SUT/test failures unless classified explicitly;
- N1-N10 concepts existing partially in prompts/stages rather than as one canonical persisted mission state machine.

## 6. Frozen construction invariants

RC7.2 construction MUST preserve these invariants:

1. ReleaseBatch is the highest business root.
2. Requirement and SST remain mandatory business traceability axes.
3. Coverage can prioritize or reveal missing obligations but cannot directly create orphan test cases.
4. N1-N10 are runtime state-machine semantics, not ten permanent Agents.
5. Agent role is distinct from Worker and Session.
6. Session is disposable; R1 is truth.
7. N7 execution does not silently absorb N2/N3/N4/N5/N6 responsibilities.
8. N8 classifies failures and creates semantic back-edges.
9. Worker remains least-privilege/STRICT; missing capability is handled by governed lease/delegation.
10. Browser/model/data resources are runtime resources with ownership/lease semantics.
11. Existing RC7.1 graph/version contracts remain backward compatible unless an explicit migration is implemented and qualified.
12. No mocked tool output, UI-only PASS or Agent self-report may substitute for R1/Evidence qualification.

## 7. Phase 0 exit decision

Phase 0 is complete for repository construction when:

- this baseline is committed on `work/rc7.2`;
- the frozen design/contracts 00-05 are present in the same history;
- construction starts from the design baseline, not an older RC7.1 SHA;
- Phase 1 extends the existing R1 runtime rather than creating a parallel truth store.

Field qualification remains a later explicit phase and is not claimed by this document.
